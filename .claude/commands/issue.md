# 이슈 생성

대화에서 논의된 내용(버그, 기능, 작업)을 정리해 이슈 제목/본문을 작성하고, 가능하면 실제로 이슈를 생성한다.

---

## Phase 1: 사전 확인

1. 이슈로 만들 내용을 파악한다 — 대화 맥락에서 이미 명확하면 그대로 쓰고, 불명확하거나 여러 건이 섞여 있으면 사용자에게 무엇을 이슈로 만들지 확인한다
2. 특정 코드/브랜치와 관련 있으면 `git status`, `git branch --show-current`로 현재 상태를 확인해 본문 작성 시 참고
3. `gh issue list --search "<키워드>"`로 비슷한 이슈가 이미 있는지 가볍게 확인한다 (중복 생성 방지) — 겹치는 게 있으면 사용자에게 알리고 계속 진행할지 확인

---

## Phase 2: 이슈 제목/본문 작성

1. **본문은 반드시 `.github/ISSUE_TEMPLATE/issue-form.md`의 양식을 그대로 따른다.** 이 저장소는 해당 템플릿이 있으므로 임의의 자유 형식으로 대체하지 않는다. `Read`로 템플릿을 먼저 읽고, 그 섹션 제목과 순서를 그대로 유지한 채 각 섹션을 채운다:
   - `📌Summary` — 이슈 한 줄 요약
   - `🛠작업내용` — 무엇을 할 건지 / 왜 필요한지
   - `✅Tasks` — 체크리스트 형태의 하위 작업 목록 (`- [ ] 항목`)
   - `🔍Notes` — 참고 링크, 스크린샷, 논의 사항 (없으면 "없음"으로 명시)
   - 템플릿 파일 자체가 바뀌어 있을 수 있으니, 과거 대화나 기억이 아니라 **매번 다시 읽어서** 최신 섹션 구성을 기준으로 삼는다
2. **제목**은 간결하게 — 무엇을 할 건지 한눈에 드러나야 함
3. `✅Tasks`는 대화에서 나온 구체적인 작업 단위로 쪼갠다 — 뭉뚱그린 항목 하나로 때우지 않는다

---

## Phase 3: 생성 — `gh` CLI 유무로 분기

1. `gh --version`으로 설치 여부 확인 (기존에 열려있던 셸은 PATH가 갱신 안 됐을 수 있으니 새 셸이거나 전체 경로로 재확인)

2. **`gh`가 있고 인증돼 있으면** (`gh auth status`로 확인)
   - 작성한 제목/본문을 사용자에게 보여주고 **승인받은 뒤**
   - `gh issue create --title "<제목>" --body "$(cat <<'EOF'
     <본문>
     EOF
     )"` 실행
   - 생성된 이슈 URL을 사용자에게 전달

3. **`gh`가 없거나 미인증이면**
   - `git remote get-url origin`에서 `<owner>/<repo>`를 파싱해 새 이슈 작성 URL을 만들어 전달:
     `https://github.com/<owner>/<repo>/issues/new?template=issue-form.md`
   - 작성한 제목/본문 텍스트를 그대로 보여줘서, 사용자가 그 URL을 열어 붙여넣기만 하면 되게 한다

---

## 주의사항

- 이슈 생성은 공유 상태를 바꾸는 행동 — **제목/본문을 반드시 먼저 보여주고 승인받는다**
- 라벨(`labels`), 담당자(`assignees`)는 템플릿상 비어있으므로 사용자가 명시적으로 요청했을 때만 추가
- 여러 작업이 섞여 있으면 하나의 이슈로 뭉치지 말고, 이슈를 나눠야 하는지 먼저 사용자에게 확인
